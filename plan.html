arxiv-fixes: architecture plan

status: draft created: 2026-10-11

This repo keeps nontrivial fixes to arXiv sources so that each paper compiles and the resulting PDF is usable. This page records what "fixed" means, how each paper directory is laid out, what is tracked in git, and how CI builds the PDFs.

Decision: stays separate

Decided 2026-10-11: this repo is not folded into the notes vault, neither merged nor as a submodule. The vault ignores *.pdf by default while this repo ships PDFs, the vault has no CI, and at ten papers this repo is small enough that a separate history costs nothing. Cross-link by URL instead of by submodule pointer.

1. Goal and non-goals

The goal is minimal modernization: the source compiles under a stock TeX Live, and the PDF has working bookmarks, hyperlinks in color, and readable diagrams. Fixes stay cosmetic and structural. They never change the mathematics.

Explicitly out of scope: retypesetting papers from scratch, tracking new arXiv versions (the version is pinned in the directory name, e.g. 0910.4460v2), and fixing papers whose source is lost beyond repair. A paper whose conversion is lossy is still accepted, but the loss is documented in the directory readme (as hep-th_9408074v2/readme.md does).

2. Directory layout contract

One directory per paper, named after the arXiv identifier with / replaced by _ and the version appended. The canonical entry point is <dirname>.tex at the directory root. Figures, .eps files, and a committed .bbl (upstream .bib is usually absent) live beside it.

Conversion helpers such as convert.py and intermediate files such as body.tex or converted.tex are work logs, not deliverables. Lasting notes from a conversion go in the directory readme.md; the helpers and intermediates are removed before an entry is marked done. Three directories currently violate the entry-point rule and are grandfathered until touched (see section 7).

3. The "fixed" checklist

Every entry should converge on this list, drawn from what past entries actually needed:

  • documentstyle becomes documentclass; the file compiles under current TeX Live.
  • Fake section headings (\noindent{\it{...}}) become real \section structure so bookmarks and the table of contents work.
  • hyperref with color links and back references.
  • eqnarray* becomes align*; ad-hoc proof environments become proof.
  • Broken diagrams move to tikz-cd; broken picture overlaps and obscured labels are fixed.
  • A missing bibliography is reconstructed and committed as .bbl.
  • Every change, plus any known remaining defect, is recorded in the index.md entry.

4. What git tracks

Sources are tracked; build products are not. The PDFs readers download are produced by CI (section 5), which ends the current drift where two papers have locally built PDFs that are untracked while the rest are committed.

5. CI design

CI builds PDFs; git does not store them. A full rebuild of all ten papers costs on the order of \(10 \times 60\,\mathrm{s} \approx 10\,\mathrm{min}\), so a full build is affordable, but there is no reason to pay it when one paper changes. The workflow therefore builds only changed paper directories:

  • Detect. Check out with full history and diff names against the base commit; map changed files to paper directories; emit a JSON matrix. A commit touching one paper builds one directory. A manual dispatch builds all.
  • Build. One matrix job per changed directory runs latexmk -pdf -interaction=nonstopmode under TeX Live and uploads the entry-point PDF as an artifact. Each job is independent, so a broken paper fails without blocking the rest.
  • Deploy. A deploy job merges the fresh artifacts with the previously deployed PDFs (unchanged papers keep their existing files), assembles a public/ directory with the index pages, and publishes it. The current workflow uploads the whole repo; switch it to the assembled directory so intermediates never ship.

6. The index contract

index.md is the manifest. One entry per paper directory: identifier and version, title and authors, abstract, a relative link to the built PDF, the list of changes made, and any warnings about remaining defects. CI should validate the manifest: every paper directory has an entry, and every linked PDF is produced by the build. The existing index.html is a hand-exported render of the index; regenerating it from index.md at deploy time is a later step, not part of this plan.
